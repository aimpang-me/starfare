# Booking and replay follow-up

Scope: the public booking desk, MCP booking list, leaderboard, flight manifest, replay and dispatcher notes. Based on `main` at `7839868`, after PR #12. No deployment, engine numerical change, score change or benchmark-suite recut is included.

## Changes

- `poolView` supplies the same seasonal booking pool to MCP, the home page and the public `/hails.json` endpoint. `/board.json` carries that pool too. Scored catalog reference bookings remain available and are labelled separately; older seasonal winners are excluded from the current season's board.
- The browser admits the generated bookings into its engine catalog. The desk has search and pages of 20, calculates route previews only on selection, and refreshes the pool after a season reset. A stale desk stops advertising its old bookings while refreshing. Agent prompts include the booking ID, because generated titles can repeat.
- New dispatched runs snapshot their booking identities, passenger parties, ship seats and intended stops. The public record and home-map rows expose this manifest. Older records explicitly label reconstructed metadata or missing values.
- Both pages use the same manifest presentation code, published by the build as `/assets/flight-view.js`. Physical segments map to original stop numbers, so a diversion does not accidentally board or drop another booking. Shared-flight receipt rows use each booking's own scores, quoted arrival, actual arrival and fare.
- Public flight segments identify their dispatched or replanned leg. The flight replay selects that stored arc. The home map fetches the same stored arcs instead of asking a generic planner to invent a replacement path. Old records retain a labelled reconstruction fallback; straight map guides are identified as such.
- Orbit arrival is distinct from landing. The home map retains flights held before launch and reports checkpoints as awaiting an agent. Finished replays show arrived at the exact final track time. Browser dates now use the connector's minute-rounding convention.
- Dispatcher logs keep the agent's notes and show every booking's dispatch quote on shared flights. The site still does not dispatch flights itself.
- The method page and flight labels state the impulsive-transfer approximation and the unresolved propulsion-feasibility limit.

Shared-flight rendering uses the existing engine/benchmark data shape. This does not add a new public multi-booking acceptance tool: hosted `take_hail` still accepts one booking; the benchmark/game seam already supports shared tasks.

## Additional engine defect exposed by the browser check

Run:

```sh
node audit/shared-flight-timing.mjs
```

For SF-04 carrying `ceres-shift` then `phobos-commute`, seed `2`, request JD `2461700.5`, the engine records arrival at Mars Base at `2030-07-23 01:00`, but departure toward Phobos at `2030-07-23 00:22`. The unrounded overlap is 37.7 minutes. These are simulated sky dates.

Cause: `arrivePhase` in `world/engine/sol-rides.js` advances to `N.dep_jd` after a drop-off. Its clamp to actual landing plus dwell applies only when passengers board. A later empty pickup leg can therefore depart before the preceding landing.

Affected flight pages show a recorded-timing warning and preserve the stored numbers. This defect was left open in PR #13. The Engineering follow-up in `SHARED-FLIGHT-TIMING.md` corrects continuation ordering and records its engine/bundle/suite prerequisites. The separate propulsion-model limitation remains open.
